# bringup-check

[English](README.md)

**SO-101이 안 움직이거나, 떨거나, 서보 하나가 뜨거운데 이유를 모르겠을 때.**
`bringup-check`는 Feetech 서보가 원래 보내 주는 숫자(전압·온도·부하·전류·오류 상태·위치 한계)를 읽어, 가장 가능성 높은 **셋업 원인과 해볼 것**을 사람 말로 알려 줍니다.

기존 도구는 "모터가 대답하는지"까지만 봅니다. 이 도구는 **왜** 이상하게 동작하는지에 답하려고 합니다.

```
[문제] 4번 모터(wrist_flex)부터 끝까지 응답이 없습니다
    무슨 일인지: 응답한 모터: [1, 2, 3] / 응답 없음: [4, 5, 6]. 데이지 체인이 한 지점에서 끊긴 모양입니다.
    해볼 것: 3번 모터(elbow_flex)와 4번 모터(wrist_flex) 사이 케이블과 커넥터를 다시 꽂거나 교체해 보세요.
```

## 왜 만들었나

SO-100/101, Reachy Mini 같은 취미용 로봇의 공개 사고 사례 66건(GitHub 이슈·포럼)을 모아 분류했습니다. **66건 중 37건이 셋업 문제**(전원·배선·조립·캘리브레이션)였고, 코드나 부품 불량이 아니었습니다. 아래 진단은 각각 그 실제 사례를 바탕으로 만들었습니다.

| 진단 | 예시 결과 | 바탕이 된 사례 |
|---|---|---|
| 체인 단선 | "3번과 4번 모터 사이 케이블을 확인하세요" | LeRobot #3131 등 |
| 한 모터만 무응답 | "ID 설정이 빠졌거나 서보 고장" | LeRobot #605, Pollen 포럼 |
| 과전압·저전압 | "모터 6개 모두 과전압: 7.6V (보호 상한 7.0V)" | Reachy Mini #589 |
| 정격과 다른 어댑터 | "7.4V용 서보에 12.1V" (`--servo-rating` 지정 시) | Arduino 포럼 |
| 체인 뒤로 전압 하락 | 헐거운 커넥터·가는 케이블 | 전원·배선 사고 다수 |
| 한 서보만 뜨거움 | "다른 서보와 바꿔 끼워 열이 따라가는지 보세요" | ROBOTIS 포럼 |
| 위치 한계·모드 설정 오류 | "위치 한계가 잘못됐습니다 (2100 ≥ 2100)" | Pollen 포럼 |
| 캘리브레이션 이탈·경계 | "엔코더 경계(0/4095) 근처" | LeRobot #3193, #1026 |
| 쥔 채 힘쓰는 그리퍼 | "멈춘 채 계속 힘을 쓰고 있습니다 (부하 85%)" | LeRobot #2819 |
| (선택) 부하 시 전원 처짐 | "5.0V → 4.1V로 떨어졌습니다" | Arduino 포럼 |

## 설치

```bash
pip install "bringup-check[hardware] @ git+https://github.com/bluvtx09/bringup-check"
```

LeRobot을 이미 쓰고 있다면 서보 SDK(`feetech-servo-sdk`)는 이미 설치돼 있습니다.

## 사용법

```bash
# 로봇 없이, 재현한 사고 시나리오로 모든 진단 보기
bringup-check --demo all

# 내 로봇 (읽기만 함: 아무것도 움직이거나 쓰지 않음)
bringup-check --port /dev/ttyACM0 --servo-rating 7.4 --calib auto

# 선택: 모터에 힘을 넣고 현재 자세를 5초 유지하며 전원 검사
bringup-check --port /dev/ttyACM0 --hold-test 5
```

- `--calib auto`는 LeRobot 캘리브레이션 파일을 찾아, 지금 연결된 팔과 맞는 파일을 골라 씁니다.
- `--ids`는 **데이지 체인 순서대로** 적습니다(기본 `1,2,3,4,5,6`). 단선 위치 추정이 이 순서를 씁니다.
- `--lang en|ko`로 언어를 고릅니다(기본은 시스템 언어).
- 모터에 힘을 넣는 옵션은 `--hold-test`와 아래의 `--first-run`뿐입니다. `--hold-test`는 목표를 현재 위치로 맞춘 뒤 켜서 튀지 않고, 끝나면 원래 토크 상태로 되돌립니다. 그래도 팔을 받칠 준비를 하세요.
- `[문제]`가 있으면 종료 코드 1을 돌려줍니다.

## 첫 실행 안전 모드 (v0.6 신규)

새로 조립한 팔에 처음 전원을 넣을 때 쓰는 모드입니다. 한 단계씩 확인하고, 앞 단계를 통과해야 다음으로 넘어갑니다.

1. **전원과 배선:** 모든 모터가 응답하고, 전압이 정상이고, 오류 표시가 없는지
2. **캘리브레이션:** LeRobot 캘리브레이션 파일이 팔과 맞고, 모든 관절이 범위 안에 있는지
3. **저출력 첫 동작:** 출력 제한을 20%로 두고 한 모터씩 범위 가운데 쪽으로 4° 움직였다가 돌아옵니다
4. **정상 출력:** 같은 동작을 50%, 100%(그리퍼는 LeRobot과 같이 50%)로 반복합니다. 출력을 올릴 때마다 먼저 묻습니다

모터에 전원이 들어가 있는 동안 모든 값을 계속 지켜봅니다. 서보가 오류를 보고하거나, 온도가 한계 10°C 안쪽까지 오르거나, 전원이 15% 넘게 떨어지면 **모든 모터의 전원을 즉시 끕니다.** 힘만 쓰고 움직이지 못하는 관절은 그 관절만 멈춥니다. 낮은 출력에서는 팔 무게 때문인 경우가 많아서 다음 단계에서 다시 확인하고, 정상 출력에서도 못 움직이면 나사 조임, 끼인 케이블, 혼 조립 같은 걸림 문제로 알려 줍니다. 끝나면 원래 출력 제한과 전원 상태로 되돌립니다. 오류가 나거나 Ctrl+C로 멈춰도 마찬가지입니다.

```bash
# 먼저 팔을 접어서 받침 위에 올려 두세요
bringup-check --first-run --port /dev/ttyACM0

# 가상의 팔로 어떻게 동작하는지 보기 (정상, 팔꿈치 걸림, 약한 전원, 고장 난 서보 등)
bringup-check --first-run-demo all
```

가상의 팔로만 시험했고 실제 SO-101에서는 아직입니다. 기준값은 시작점입니다.

## 텔레오퍼레이션 과부하 가드 (v0.3 신규)

팔로워 서보가 타는 흔한 경로가 있습니다. 텔레오퍼레이션 중 팔로워가 막혀 있는데(그리퍼가 이미 물체를 쥐었거나, 관절이 테이블에 눌려 있거나) 리더는 계속 더 가라고 명령하는 경우입니다(LeRobot #2819). 서보는 멈춘 채 최대 부하로 계속 밀다가 과열됩니다.

가드는 LeRobot의 로봇 종류 하나로 바로 끼워 쓰는 방식입니다. 매 제어 주기마다 부하·위치·온도를 보고, 모터가 **막힌 상태**(부하 높음, 목표와 멀리 떨어짐, 안 움직임)로 약 1.5초 넘게 있을 때만 개입합니다.

- **팔 관절**은 미는 걸 멈추고 장애물에서 2° 물러납니다.
- **그리퍼**는 닿은 지점 바로 너머에서 *가볍게* 쥔 상태를 유지해, 물체를 떨어뜨리지 않습니다.
- 막힌 게 아니라 **팔 무게를 버티는 중인 관절**은 건드리지 않습니다. 개입 전에 2°짜리 작은 확인 동작으로 이를 구분하므로 팔이 처지지 않습니다.
- 리더를 장애물 반대쪽으로 움직이면 바로 다시 따라갑니다.

```bash
pip install "git+https://github.com/bluvtx09/bringup-check#subdirectory=plugins/lerobot_robot_so101_guarded"

# so101_follower와 인자는 같고, type만 바꾸면 됩니다
lerobot-teleoperate \
  --robot.type=so101_follower_guarded --robot.port=/dev/ttyACM0 --robot.id=my_arm \
  --teleop.type=so101_leader --teleop.port=/dev/ttyACM1 --teleop.id=my_leader
```

옵션: `--robot.guard_mode=warn`은 개입하지 않고 무엇을 했을지만 출력합니다. `--robot.guard_log=guard.csv`는 매 주기를 기록합니다(결과 이슈에 첨부해 주세요. 기준값을 다듬는 데 꼭 필요한 데이터입니다). 기존 `so101_follower` 캘리브레이션을 그대로 쓰고, `lerobot-record`에서도 작동합니다.

로봇 없이 동작 확인:

```bash
bringup-check --guard-demo
```

LeRobot 0.6.1의 실제 설정 해석·로봇 생성·`send_action` 코드로, 시리얼 버스만 단순한 서보 모델로 바꿔 시험했습니다. **실물 팔에서는 아직 시험하지 않았고**, 기준값은 출발점입니다. 주기마다 버스 읽기가 두 번 늘어납니다(수 ms).

### 내 팔에서 검증하기 (10분, 팔로워 한 대만, 리더 불필요)

```bash
so101-guard-validate --port /dev/ttyACM0 --id my_arm
```

안내에 따라 4가지를 시험합니다. 천천히 **왕복**하기와 팔을 뻗은 **자세 유지**(가드가 개입하면 안 됨), **손목으로 책 밀기**와 **그리퍼로 스펀지 꽉 쥐기**(가드가 개입해야 함)입니다. 위치는 모터 힘을 뺀 상태에서 손으로 알려 주는 방식이라 어느 쪽이 아래인지 가정하지 않고, 모든 움직임은 속도가 제한됩니다. 시험별 PASS/FAIL을 출력하고 CSV를 저장합니다. 이 CSV를 이슈에 첨부해 주시는 게 이 프로젝트에 가장 큰 도움이 됩니다. `bringup-check --analyze-log 파일.csv`로 어떤 가드 기록이든 요약할 수 있습니다.

## 녹화된 데이터셋에서 막힌 순간 찾기 (v0.5 신규, 로봇 불필요)

원격조종 데이터셋에는 리더가 명령한 위치(`action`)와 팔로워의 실제 위치(`observation.state`)가 함께 기록됩니다. 관절이 움직이지 않는데 명령과 실제 위치가 계속 멀리 떨어져 있으면, 팔로워가 막혀 있던 것입니다. 그리퍼가 물체를 쥔 채 더 닫히려 하거나, 관절이 책상을 누르고 있는 경우죠. 과부하 가드가 겨냥하는 바로 그 상황이고, `--scan-dataset`은 가드와 같은 기준으로 이 순간을 찾습니다.

```bash
pip install "bringup-check[dataset] @ git+https://github.com/bluvtx09/bringup-check"

# Hugging Face 데이터셋 이름이나 내 컴퓨터의 LeRobot 데이터셋 폴더. 여러 개를 한 번에 넣어도 됩니다
bringup-check --scan-dataset lerobot/svla_so101_pickplace
bringup-check --scan-dataset ~/.cache/huggingface/lerobot/me/my_dataset --json scan.json
```

영상은 받지 않고 `meta/info.json`과 parquet 파일만 받습니다. 관절별로 얼마나 자주, 얼마나 오래 막혔는지 보여 주고, 가장 오래 버틴 구간을 에피소드와 시각으로 알려 줘서 영상에서 바로 확인할 수 있습니다. 리더와 팔로워의 캘리브레이션이 어긋나 보이는 관절도 따로 알려 줍니다.

### 공개 SO-100/101 데이터셋 53개에서 보인 것

Hub의 공개 데이터셋 53개, 에피소드 7,731개(약 33시간)를 가드와 같은 기준(차이 그리퍼 5 / 팔 8 이상, 거의 정지, 1.5초 이상)으로 분석했습니다([목록](studies/public_datasets.txt)).

- **그리퍼가 막힌 채 쥐는 건 흔한 일입니다.** 에피소드의 53%에서 한 번 이상 나왔고, 53개 중 40개 데이터셋에 있습니다. 중앙값 3.3초, 16%는 5초 넘게, 92번은 10초 넘게 이어졌고 가장 긴 것은 16.4초였습니다.
- **팔 관절이 막히는 일은 드뭅니다.** 에피소드의 약 3%이고, 몇몇 데이터셋에 몰려 있습니다.
- **리더·팔로워 캘리브레이션 어긋남도 보입니다.** 데이터셋 6개의 관절 8개에서 나왔습니다.

주의할 점이 두 가지 있습니다. 공개 데이터셋은 대부분 익숙한 사람이 녹화하고 골라낸 것이라, 처음 원격조종할 때 벌어지는 일보다 덜 극단적입니다. 그리고 데이터셋에는 부하와 온도가 없어 위치만으로 찾은 후보입니다. 그래도 결과는 키트 판매처의 A/S 경험과 같은 쪽을 가리킵니다. 팔로워 서보가 가장 오래 세게 버티는 곳은 물체를 쥐고 있는 그리퍼입니다.

## 결과를 공유해 주세요

진단 기준값은 공개 사례에서 잡은 **출발점이고, 아직 실물로 검증되지 않았습니다.** 정상이든 아니든 로봇에서 돌려 보셨다면 아래 명령의 출력을 이슈로 올려 주시고, 진단이 실제 원인과 맞았는지 알려 주세요.

```bash
bringup-check --port /dev/ttyACM0 --calib auto --share
```

→ [결과 공유하기](https://github.com/bluvtx09/bringup-check/issues/new?template=diagnosis-report.md)

`--share` 출력에는 모터 측정값과 진단 코드만 들어갑니다. 파일 경로나 포트 이름은 들어가지 않습니다.

### 키 하나로 보내기 (v0.7 신규)

실물 로봇으로 실행한 뒤(`--port`, `--first-run`, `so101-guard-validate`) 결과를 개발자에게 보낼지 물어볼 수 있습니다. 보낼 내용을 **전부** 먼저 보여 주고, `y`를 입력할 때만 보냅니다. 기본값은 보내지 않음입니다.

- 보내는 것: 서보 측정값(전압, 온도, 부하, 전류, 위치, 한계, 상태), 진단 코드, 시험 판정, 도구·파이썬 버전, 운영체제 이름
- 보내지 않는 것: 포트 이름, 사용자 이름, 파일 경로, 로봇 ID, 캘리브레이션 파일, 원본 로그
- 관리자만 볼 수 있는 구글 폼으로 가고, 진단 기준을 다듬는 데만 씁니다.
- 터미널이 없으면(스크립트, CI) 묻지 않고, 출력과 종료 코드는 바뀌지 않습니다. 전송에 실패하면 실패했다고만 알립니다.
- 질문을 끄려면 `--no-send`를 붙이거나 `BRINGUP_CHECK_NO_SEND=1`로 설정하세요.

## 문제가 생기면

| 이런 메시지가 나오면 | 이렇게 하세요 |
|---|---|
| `pip install "...@ git+https://..."`이 git 오류로 실패 | GitHub에서 바로 설치하려면 [Git](https://git-scm.com/downloads)이 필요합니다. 설치하거나, 저장소를 ZIP으로 받아(**Code → Download ZIP**) 압축을 풀고 `pip install "./bringup-check-main[hardware]"`를 실행하세요. 가드 플러그인은 `pip install --no-deps ./bringup-check-main/plugins/lerobot_robot_so101_guarded`로 설치합니다(LeRobot이 이미 설치돼 있어야 함). |
| `포트 ...를 열 수 없습니다` | 포트 이름을 확인하세요. Windows는 `COM3`, `COM4` 등(장치 관리자 → 포트), Linux는 `/dev/ttyACM0`, macOS는 `/dev/tty.usbmodem...`입니다. `lerobot-find-port`로도 찾을 수 있습니다. 같은 포트를 쓰는 다른 프로그램(LeRobot을 돌리는 다른 터미널, Feetech 디버그 프로그램, Arduino IDE)을 닫으세요. Linux에서 권한 오류라면 `sudo usermod -aG dialout $USER` 후 다시 로그인하세요. |
| `scservo_sdk가 없습니다` | `pip install feetech-servo-sdk` (`[hardware]`나 LeRobot을 설치하면 함께 깔립니다) |
| "모터가 하나도 응답하지 않습니다" | 도구가 알려 주는 다섯 가지 점검을 따라 하세요. 가장 흔한 원인은 전원이 꺼졌거나 잘못된 경우(SO-101 팔로워와 리더는 전압이 다를 수 있음)와 컨트롤러 보드 점퍼 위치입니다. |
| `--calib auto`가 파일을 못 찾음 | `$HF_LEROBOT_CALIBRATION`, `$HF_HOME/lerobot/calibration`, `~/.cache/huggingface/lerobot/calibration`을 찾습니다. 파일 경로를 직접 주세요: `--calib path/to/my_arm.json` |
| `so101-guard-validate`가 캘리브레이션 파일이 없다고 함 | `lerobot-calibrate` 때와 같은 `--id`를 쓰거나, `--calibration_dir`로 폴더를 알려 주세요. |
| `lerobot-teleoperate`가 `so101_follower_guarded`를 모름 | 플러그인을 LeRobot과 같은 파이썬 환경에 설치하세요(`pip show lerobot_robot_so101_guarded`로 확인). 가드는 파이썬 3.10 이상이 필요하고 LeRobot 0.6.1로 시험했습니다. 다른 버전에서 안 되면 오류 메시지와 `pip show lerobot` 결과를 이슈로 올려 주세요. |
| 결과를 보낼지 묻는 질문이 나옴 | 선택 사항이고 기본값은 보내지 않음입니다(위 설명 참고). `--no-send`로 끌 수 있습니다. |

그 밖의 문제는 전체 출력과 함께 [이슈로 올려 주세요](https://github.com/bluvtx09/bringup-check/issues/new). 학생이 관리하고 있어서 답이 며칠 걸릴 수 있습니다.

## 한계

- Feetech STS/SMS 버스 서보(SO-100/101의 STS3215)만 지원합니다. Dynamixel 등은 아직 지원하지 않습니다.
- PWM 서보(SG90, MG996R 등)는 상태를 보내 주지 않아 진단할 수 없습니다.
- 실물 SO-101에서는 아직 돌려 보지 않았습니다. 테스트는 공식 SDK의 호출 형식을 흉내 낸 가짜 버스와, 실제 사고를 흉내 낸 시나리오로 했습니다.
